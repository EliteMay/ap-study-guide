# ChatGPT作業ルール

このファイルは、GitHub上の `EliteMay/ap-study-notes` をChatGPTで直接保守するときの詳細ルールです。短い必須事項は `docs/ai/AI最重要ルール.md` を優先します。

## 1. 基本ワークフロー

既存サイトを変更するときは、次の順で進めます。

1. `README.md` を確認する。
2. `docs/仕様書.md` と `docs/作業報告書.md` の関連箇所を確認する。
3. 今回の対象ファイルと関連ファイルをGitHubから読む。
4. 目的・変更範囲・守る仕様・完了条件を整理する。
5. GitHub上の既存ファイルを直接修正する。
6. 可能な範囲で構文・リンク・JSON・参照整合を確認する。
7. `docs/作業報告書.md` を更新する。
8. 仕様変更があればREADME・仕様書も更新する。

結果が大きく変わる重要な曖昧さがなければ、確認待ちで作業を止めない。

## 2. ChatGPTに任せてよいこと

- GitHub上のREADME・仕様書・作業報告書・コード・JSONを読む。
- HTML/CSS/JavaScript/JSON/Markdownの直接修正。
- 用語解説や過去問解説の改善。
- マニフェストや索引の整合修正。
- GitHub Pages向けの静的サイト調整。
- README、仕様書、作業報告書の更新。
- 必要な検査スクリプトやチェックツールの改善。

## 3. Codexまたは実機確認が向くこと

- ブラウザ操作を伴う不具合再現。
- 大規模な複数ファイル自動テスト。
- Electronビルド、Setup.exe生成。
- OS依存機能。
- GitHub上で読めるファイルだけでは判断できない実行時不具合。

これらも最初からCodexへ丸投げせず、ChatGPTで確認・修正できる範囲を先に進める。

## 4. 現在のページ配置を維持する

- ホーム入口: `index.html`
- 各単元ページ: `html/`
- 共通スタイル: `css/style.css`
- 学習データ: `json/`
- PDF原本: `sources/`
- 保守文書: `docs/`
- AI向け文書: `docs/ai/`

大きな配置変更は、理由・影響ファイル・メリット・デメリットを示してから行う。

## 5. 変更してはいけない識別子

用語JSON・詳細JSONでは、根拠なく次を変更しない。

```text
id
term
category
```

過去問JSONや索引では、根拠なく次を変更しない。

```text
id
examRound
questionNumber
title
file
problemFile
sourcePdf
sourceProblemFile
answerTargets
expectedAnswers
```

## 6. JSON分離ルール

- `json/terms/`: 検索・一覧向けの短い定義。
- `json/details/`: 初学者説明、具体例、試験ポイント、ひっかけ、午後での使い方。
- `json/past-problems/`: 問題文、設問、選択肢、表の起こし。
- `json/past/`: 設問別解説。
- `sources/`: PDF原本。

大量データをHTMLやJavaScriptへ直書きしない。

## 7. 解説文章の品質

次のような、どの用語にも貼れる薄い文を使い回さない。

```text
万能な対策ではない。
名前だけで判断しない。
目的・対象・限界を分けて考える。
何をできて何をできないかを覚える。
```

観点自体は使ってよいが、その用語固有の内容へ具体化する。

出力前に次を確認する。

```text
。。
という意味の用語
万能な対策
何をできて何をできないか
```

## 8. 一括編集の注意

- 501語や480語を一気に書き換えると説明が薄くなりやすい。
- 個別品質を上げる作業は1カテゴリまたは重要語20件程度を目安にする。
- 全件を触る場合は、機械的な構文・表記・参照修正と、内容改善を分ける。

## 9. GitHub Pages向け注意

- 公開URLは `https://elitemay.github.io/ap-study-notes/` を想定する。
- `index.html` はルートに維持する。
- `.nojekyll` を維持する。
- ルート絶対パス `/json/...` より、現在の相対パス構成を維持する。
- `fetch()` はGitHub PagesやLive ServerなどHTTP(S)経由で確認する。
- APIキーや秘密情報を公開リポジトリに入れない。

## 10. 完了前チェック

### JSONを変更した場合

- JSON構文エラーがない。
- ID重複がない。
- terms/detailsの対応が崩れていない。
- マニフェスト件数と実データ件数が一致する。

### 過去問を変更した場合

- `problemFile` と `sourceProblemFile` を混同していない。
- 問題文側 `targets` と解説側 `answerTargets` が一致する。
- `expectedAnswers` を落としていない。
- PDF原本と問題文JSONを未確認なら、その旨を明記する。

### HTML/CSS/JSを変更した場合

- 参照パスが存在する。
- JavaScript構文エラーがない。
- GitHub Pagesのサブパスで致命的に壊れない。
- 主要ボタンや表示は、実ブラウザ確認できたか／できていないかを分けて報告する。

### すべての変更

- READMEと仕様書に矛盾を作っていない。
- `docs/作業報告書.md` を更新した。
- 確認していないものを「確認済み」と書いていない。

## 11. 作業報告書へ残すこと

- 今回の依頼内容。
- 確認したファイル。
- 変更したファイル。
- 修正した不具合・追加した機能。
- 実施した検査。
- 未確認事項。
- 残課題。

同じ失敗が繰り返されそうな場合は、このファイルまたは `AI最重要ルール.md` も更新する。
