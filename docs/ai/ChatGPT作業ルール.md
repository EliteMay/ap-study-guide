# ChatGPT作業ルール

このファイルは、ChatGPTにこのサイトの相談、文章・JSON・ページ・文書案の作成を依頼するときの詳細ルールです。最初に使う短い指示は `docs/ai/AI最重要ルール.md` にまとめ、Project instructions または依頼文の冒頭へ設定します。

## 1. 最初に必ず読むファイル

ChatGPTへ依頼するときは、ZIP一式を渡して構いません。ただし、最初に `docs/ai/AI最重要ルール.md` の本文を Project instructions または依頼文の冒頭に設定してください。長い文書は必要な作業に関係する部分だけ参照させます。

```text
docs/ai/AI最重要ルール.md（必須。Project instructionsに設定）
README.md（サイト構造や追加手順が必要な場合）
docs/仕様書.md（画面仕様やデータ仕様が必要な場合）
docs/作業報告書.md（過去の変更経緯が必要な場合）
docs/ai/ChatGPT依頼用プロンプト.md（依頼文を作る場合）
docs/ai/ChatGPT作業ルール.md（詳細な禁止事項を確認する場合）
```

既存サイトへ取り込む成果物案を依頼する場合は、依頼文の冒頭に次の確認文を入れます。質問、整理、説明、調査だけの依頼では不要です。

```text
docs/ai/AI最重要ルール.md の指示に従ってください。
今回はまだ編集を始めないでください。
まず作業前確認表を返し、指定されたファイルまたはIDと変更禁止項目を確認してください。
過去問を扱う場合は、problemFile と sourceProblemFile の使い分けも答えてください。
確認内容が正しく、私が作業開始と伝えた後だけ成果物を作ってください。
```

取り込み前提の成果物案で、この確認を返さずに生成を始めた場合、または確認表の回答が誤っている場合は、その出力は採用しないでください。

## 2. ChatGPTに任せてよいこと

- サイトの構造、仕様、学習内容について相談、整理、説明、調査を行う。
- 用語解説の文章を分かりやすくする。
- 具体例を追加する。
- 午前問題・午後問題での見方を説明する。
- 似た用語との違いを書く。
- 過去問解説の下書きを改善する。
- 指定範囲のJSON改善案、HTML/CSSの修正案、README・仕様書の修正案、テンプレートや提出用成果物案を作る。
- 必要であれば、Codexへ渡しやすいZIPや引き継ぎ文の形にまとめる。

## 3. ChatGPTに任せないこと

- ファイル全体の整合確認。
- JSONの最終取り込み。
- ID重複、件数ズレ、リンク切れ確認。
- 既存プロジェクト内のHTML/CSS/JS、設定、ファイル構成の最終反映。
- README、仕様書、作業報告書の既存ファイルへの最終反映。
- 「確認しました」と言うだけの検証。

これらはCodexで行います。

## 3-1. 現在のページ配置を維持する

- ホーム入口はルートの `index.html` とする。
- 各単元ページ、テスト、テンプレートは `html/` に置く。
- 共通スタイルは `css/style.css` に置く。
- マニフェスト、学習JSON、PDFは現在どおりルート配下の `json/`、`sources/` などに維持する。
- この配置を変更する案が必要な場合は、通常の文章改善とは分けて理由を明示し、Codex確認対象とする。

## 3-2. Codex確認を求めるタイミング

最終的に採用して本番ファイルへ反映する判断はCodexが行います。ただし、ChatGPTが指定範囲の成果物案を作る途中で、毎回Codexの確認を要求する必要はありません。

取り込み前提の成果物案では、通常は指定された範囲で作れる案を完成させ、最後に `Codex確認推奨なし` と書きます。相談、整理、説明、調査だけの回答では、この表示は不要です。

次の状況では、案の作成を止めずに進めた上で、回答末尾に `Codex確認推奨` を付けてください。

- READMEと仕様書の解釈が分かれ、どちらを前提にすべきか判断が必要な場合。
- READMEと今回のユーザー指示が衝突する場合。
- 依頼された1ファイルやID以外にも変更が必要になりそうな場合。
- `id`, `term`, `category`, `problemFile`, `sourceProblemFile`, `answerTargets`, `expectedAnswers` など、他データと一致させる項目に影響する場合。
- HTML/CSS/JavaScript、リンク、索引、検査ツールの変更に波及しそうな場合。
- PDF原本や問題文JSONを見なければ、答案や試験回を確定できない場合。
- 不明点が大きく、暫定案を採用すると誤りが混ざる危険がある場合。

`Codex確認推奨` には、理由、Codexに確認したいこと、ChatGPT側で作成できた暫定案を簡潔に書きます。ユーザーは、その確認が必要だと判断した場合だけCodexへ渡します。

## 4. 絶対に変更してはいけないもの

用語JSON・詳細JSONでは、以下を変更してはいけません。

```text
id
term
category
```

過去問JSONや索引では、根拠がない限り以下を変更してはいけません。

```text
id
examRound
questionNumber
title
file
problemFile
sourcePdf
sourceProblemFile
answerTargets
expectedAnswers
```

## 5. 禁止する書き方

次のような、どの用語にも貼れる薄いテンプレ文は禁止です。

```text
問題では「使う場所」と「防げること」をセットで思い出す。
何をできて何をできないかを一文で説明できるようにする。
単語だけでなく、どの場面で使い、何を防ぎ、何は防げないかまで問われる。
目的・対象・限界を分けて考える。
名前だけで判断しない。
万能な対策ではない。
```

これらの観点自体は大事ですが、そのまま使い回すと解説が薄くなります。必ず用語固有の内容に置き換えてください。

悪い例:

```text
SQLインジェクションは、目的・対象・限界を分けて考える。
```

良い例:

```text
SQLインジェクションは、入力値がSQL文の一部として解釈されることで起きる。対策は、入力値を文字列として扱わせるプレースホルダが中心で、画面側の入力チェックだけでは不十分。
```

## 6. 二重句点・機械的表現を禁止する

次のような出力は禁止です。

```text
ランサムウェア = 身代金を要求するマルウェア。。
DNS = 名前解決。。
```

出力前に、次の文字列が残っていないか確認してください。

```text
。。
という意味の用語
万能な対策
何をできて何をできないか
使う場所と防げること
```

## 7. ZIPで渡しても作業範囲は絞る

ZIPで全ファイルを渡すのは問題ありません。目的は、ChatGPTにサイト全体の構造を読ませることです。

ただし、全ファイルを一括編集してはいけません。依頼ごとに、次のように作業範囲を明記してください。

```text
今回触ってよいファイル:
json/details/security-details-crypto-pki.json

今回触ってよいID:
sec-101 から sec-120 まで
```

または:

```text
今回触ってよいファイル:
json/past/security-past-h27-s.json

今回の目的:
平成27年春期 午後問1の設問別解説だけを改善する
```

## 8. 全件一括の薄い改善を禁止する

501件すべてを一気に書き換える場合、内容が薄くなりやすいです。原則として、次のどちらかにしてください。

- 1カテゴリだけ改善する。
- 重要語20件程度だけ改善する。

全件を触る場合は、軽い文言整理だけにし、重要語の個別改善とは分けてください。

## 9. 出力前チェック

既存サイトへ取り込む成果物案を返す場合は、回答末尾へ次のチェック結果を書いてください。相談、整理、説明、調査だけの場合は不要です。

```text
出力前チェック:
- Markdownの指示を読んだ: はい
- 作業範囲外のファイルを変更していない: はい
- 変更禁止の識別子・参照項目を変更していない: はい / 該当なし
- 禁止テンプレ文や二重句点がない: はい / 該当なし
- JSON案の場合、JSONとして読める形を保っている: はい / 該当なし
- Codex確認推奨: なし / あり（理由は後記）
```

このチェックが付いていない場合は、Codexで取り込む前に差し戻してください。

## 10. Codexへ戻すときのルール

既存サイトへ取り込みたいChatGPTの成果物案は、そのまま本番ファイルへ入れません。Codexへ渡して、成果物の種類に応じて以下を確認します。

- JSON案では、JSONとして読み込めるか、件数と識別子・参照項目が維持されているか。
- HTML/CSS案では、既存画面、リンク、読み込み、表示に影響する箇所がないか。
- README・仕様書案では、最上位仕様であるREADME、今回の指示、既存方針と矛盾しないか。
- 文章案では、禁止テンプレ文や誤った断定が残っていないか。
- 取り込む場合、README、仕様書、作業報告書へ必要な追記があるか。

## 10-1. 良くなかった点の記録ルール

ChatGPTから受け取った成果物案をCodexで確認し、不採用部分や危険な点を見つけた場合は、`docs/作業報告書.md` に記録します。

記録する内容：

- どのZIP、どのファイル、どのカテゴリ、どのIDで起きたか。
- 何が良くなかったか。
- それを採用した場合に何が壊れるか、または何が分かりにくくなるか。
- 今回どう直したか、または採用しなかったか。
- 次回ChatGPTにどう指示すれば同じことを防げるか。

良くなかった点の例：

- Markdown仕様を読まず、実データ構造と違うJSONを作った。
- `id`, `term`, `category` など変更禁止フィールドを変えた。
- `mechanism` など、画面側で使わない古いフィールド名を追加した。
- 汎用テンプレ文を複数の用語に使い回した。
- 件数、マニフェスト、ID対応、targets対応がズレた。
- READMEや仕様書の更新を忘れた。

この記録はChatGPTを責めるためではなく、次の依頼文を強くするためのものです。発見した問題は、できるだけ具体的に残してください。

## 11. JSONや学習文章の成果物案を依頼するテンプレ

```text
docs/ai/AI最重要ルール.md の必須ルールに従ってください。
今回はまだ編集を始めないでください。まず作業前確認表を返してください。

対象:
【カテゴリ名または過去問名】

作業:
【例】details JSON の beginner, example, examPoint, trap, deepDive, commonMistakes, afternoonUse, howToRemember を改善してください。

禁止:
- id, term, category を変更しない。
- 汎用テンプレ文を使い回さない。
- 二重句点を出さない。
- 作業範囲外のファイルを変更しない。

出力:
修正後JSONと、変更内容の短い要約を返してください。
最後に出力前チェックを付けてください。
Codex確認が必要な条件に当てはまる場合だけ、理由・確認事項・暫定案を `Codex確認推奨` として付けてください。

確認表が正しければ、次のメッセージで作業開始と伝えます。
```
